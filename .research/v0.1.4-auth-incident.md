# v0.1.4 — sign-in instantly fails on fresh Web Store install

**Symptom:** clicking "Sign in" on a freshly-installed copy of v0.1.4 from
the Chrome Web Store shows "Authorization page could not be loaded"
within milliseconds. No network request to Supabase resolves; the auth
window flashes and dies.

**Affected extension:** `hnfolienncfklkgmdjjmhhegglimlamg` (Web Store ID).

**Local dev** is unaffected because it installs under a different ID.

---

## Root cause

The Chrome Web Store **replaces the `key` field of the manifest on upload
with its own keypair.** This is documented Chrome behavior, but it was
mis-stated in the original repo plan as "the key locks the ID across dev
and Store". It does not.

Result:

| Surface | Extension ID | Redirect URI sent to Supabase |
|---|---|---|
| Local dev (uses our `wxt.config.ts` `key`) | `cihdmkcdjjckfhjpgoedmgfpoljebaml` | `https://cihdmkcdjjckfhjpgoedmgfpoljebaml.chromiumapp.org/` |
| Web Store v0.1.4 | `hnfolienncfklkgmdjjmhhegglimlamg` | `https://hnfolienncfklkgmdjjmhhegglimlamg.chromiumapp.org/` |

Our Supabase OAuth client only had the **dev** URI registered. When the
Web Store install hits `signIn()`, [`chrome.identity.getRedirectURL()`](../src/lib/auth/flow.ts#L35)
returns the Web-Store URI, which Supabase's `/auth/v1/oauth/authorize`
endpoint rejects with `redirect_uri` validation. The auth window opens
on the Supabase URL with the bad `redirect_uri` query, Supabase responds
with an error page that closes immediately, and Chrome surfaces
"Authorization page could not be loaded".

The "instant failure" symptom is the giveaway. A network or token issue
fails after a few hundred milliseconds. A `redirect_uri` validation
fails before any UI loads.

## Verifying the diagnosis

Anyone running v0.1.4 from the Web Store can confirm by opening the
side panel, then `chrome://extensions` → matrx-extend → service worker
→ console, and running:

```js
chrome.identity.getRedirectURL()
// → "https://hnfolienncfklkgmdjjmhhegglimlamg.chromiumapp.org/"
chrome.runtime.id
// → "hnfolienncfklkgmdjjmhhegglimlamg"
```

Local dev shows `cihdmkcdjjckfhjpgoedmgfpoljebaml` for both.

The user-visible error is in the auth log:

```
[matrx-extend][sidepanel/auth] OAuth sign-in starting
  redirectUri: "https://hnfolienncfklkgmdjjmhhegglimlamg.chromiumapp.org/"
  ...
[matrx-extend][sidepanel/auth] sign-in failed
  Error: Authorization page could not be loaded
```

---

## Hotfix (no resubmit; live in seconds)

In the **Matrx Supabase project → Authentication → URL Configuration → Redirect URLs**,
add ALL of these (keep the existing dev one too):

```
https://hnfolienncfklkgmdjjmhhegglimlamg.chromiumapp.org/
https://cihdmkcdjjckfhjpgoedmgfpoljebaml.chromiumapp.org/
```

Save. Supabase config is hot; the live extension's sign-in starts
working within seconds. No code change, no resubmit.

This is also the right long-term posture: the redirect-URI list is
allowed to contain multiple valid origins. Local dev and Store production
will continue to use different IDs; we just register both.

## Permanent fix — make this impossible to ship blind again

### 1. Diagnostic visibility

[`src/features/debug/ExtensionIdentityCard.tsx`](../src/features/debug/ExtensionIdentityCard.tsx) — admin-only Debug-tab card showing:

- `chrome.runtime.id` (the actual install ID)
- `chrome.identity.getRedirectURL()` (what gets sent to Supabase)
- The OAuth client ID we're configured with
- The Supabase URL
- A "copy diagnostics" button to paste into a bug report

If a future submission ever drifts the ID, the user can confirm and
report it in 5 seconds without us needing to build a debug build.

### 2. Startup log

[`src/lib/auth/identity.ts`](../src/lib/auth/identity.ts) — emits a
structured log on every SW boot:

```
[matrx-extend][sw/auth] extension identity
  runtime_id: "hnfolienncfklkgmdjjmhhegglimlamg"
  redirect_uri: "https://hnfolienncfklkgmdjjmhhegglimlamg.chromiumapp.org/"
  expected_ids: ["cihdmkcdjjckfhjpgoedmgfpoljebaml", "hnfolienncfklkgmdjjmhhegglimlamg"]
  matches_expected: true
```

If the install ID is NOT in the expected-list, the log is `warn`-level so
errors-only filtering still surfaces it. The expected list is in
[`src/config/identity.ts`](../src/config/identity.ts) — a one-line edit
adds a new ID.

### 3. Documentation

[`CLAUDE.md`](../CLAUDE.md) gets a "Web Store identity gotcha" section
calling out the `key`-replacement behavior and the multi-URI policy in
Supabase, so the next reviewer doesn't repeat the assumption that one
key/ID pair covers both dev and Store.

---

## Why we don't try to "match" the IDs

A natural instinct is "extract the public key from the published `.crx`
and put it in our manifest so dev matches the Store." Don't:

1. The Web Store ALREADY rewrites the `key` field on every upload. Even
   if we matched, our next submission could pick up a different ID if
   we ever re-upload from a fresh dashboard or trigger a key rotation.
2. The dev / Store split is actually useful: it means a developer
   testing locally can't accidentally hit production OAuth state.
3. The cost of "two redirect URIs registered in Supabase" is zero.

The right invariant is: **the redirect-URI list in Supabase is the
union of every install ID we expect to see.** Each new build channel
(staging unpacked, beta, store) gets its URI added; Supabase is the
source of truth.

## Lessons for the original plan

The original [`matrx-extend/.claude/skills/matrx-oauth/SKILL.md`](../.claude/skills/matrx-oauth/SKILL.md) (formerly at `matrx-oauth/SKILL.md`, root-level)
should be updated with this finding. The line "After the first publish
succeeds, put it back in subsequent versions and the IDs will match
across dev and Store" is wrong. The Store ID is independent of our
manifest's `key` no matter what we do. Plan for it.
