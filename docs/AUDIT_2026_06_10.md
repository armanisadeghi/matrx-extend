# ═══ REPOSITORY HEALTH SUMMARY ═══

**Overall condition:** An ambitious, genuinely sophisticated MV3 agent harness (~83k LOC, 386 files) with real engineering care in places — but it is **pre-hardening**. The architecture is sound; the failure-mode coverage, defense-in-depth, and operational safety nets are not yet at the level the feature surface demands. The codebase has shipped feature after feature (v0.1.52) on top of a foundation that has **zero automated enforcement** (no CI, build never typechecks) and several **structural security gaps** that the defense-in-depth was assumed to cover but doesn't.

**The three biggest risks:**
1. **`admin_only` is never enforced at tool-execution time** — only at advertisement. Combined with the **WebMCP page-bridge ignoring `admin_only` and skipping confirmation in act-mode**, a hostile allow-listed page (`*.vercel.app` is trusted!) can drive admin/action browser tools. The client correctly re-checks optional-perms and pilot-scope at execution but treats admin authority as the server's job — while also self-reporting its own `is_admin`. (P0 cluster)
2. **MV3 SW-restart amnesia.** The dispatcher's in-memory `runs` map and pending-confirmation promises live only in the service worker, which Chrome reaps after ~30s. A restart mid-stream or mid-approval drops tool results (agent hangs forever), silently downgrades act→ask, and un-pins the agent's tab. The agenda runner has a worse variant: it subscribes to stream events *after* the stream has already finished, so **every scheduled run is stuck "claimed" forever and heartbeat memory never persists.** (P0 cluster)
3. **No safety net on the release path.** No CI exists; `wxt build` never typechecks (a separate `compile` script nothing invokes); drift + migration checks are `|| true` warn-only and silently pass when DB creds are absent; and the release/ship scripts use macOS-only `sed -i ''` that is broken on Linux. A type error or a drifted tool schema ships to the Web Store unblocked. (P0)

**The three biggest opportunities:**
1. **Persist run metadata + pending confirms to `chrome.storage.session`** — one change converts the two worst P0s (SW amnesia → dropped results / orphaned confirms) into non-events; `storage.session` has exactly the right lifetime.
2. **One execution-time `admin_only` gate in `handleCall` + force-confirm for page-origin calls** — closes the entire P0 security cluster (dispatcher, WebMCP, mega-tool routers) in a few lines, turning the client into a real authority instead of trusting the server.
3. **A minimal CI pipeline (`tsc --noEmit` + `biome --error-on-warnings` + `vitest` + strict drift/migration gates)** plus a dispatcher permission-gate test matrix — converts the excellent-but-unenforced tsconfig/biome/drift tooling from decorative to load-bearing.

## ── P0 — Broken / Dangerous (fix immediately) ──

**P0-1 · Page-bridge can invoke admin tools with no confirmation.** `handleWebmcpCall` rejects only `ask-user`/`privileged` tiers (`dispatch.ts:781-791`) and never checks `handler.admin_only`; in act-mode, action-tier page calls run with no confirm (`dispatch.ts:822-828`). A trusted page posts `{__matrx_webmcp_call, toolName, args}` directly — advertisement filtering is irrelevant. *Why:* hostile allow-listed page drives admin read/action browser tools (cookies-read, CDP-read, mhtml, system info). *Fix:* in `handleWebmcpCall`, after lookup add `if (handler.admin_only && !await readIsAdmin()) reject`; force confirmation for page/frontend-origin calls regardless of mode, and label the initiator as untrusted-page in the card. **S.** dep: P0-2.

**P0-2 · `admin_only` is never enforced at execution time (cross-cutting).** `handleCall` (`dispatch.ts:382-521`) checks Zod, browser, optional-perms, pilot-scope, tier — never `handler.admin_only`. Only `visible()` (`registry.ts:152-157`) + the self-reported `is_admin` field gate admin tools. *Why:* any server-delegated admin tool to a non-admin executes (cdp_attach, parallel_for_each_tab, cookie tools); the client both computes and self-reports its own admin status. *Fix:* add an `admin_only` gate in `handleCall` resolving admin from the SW's own cached storage key, not any request field. **S.** Foundational — enables P0-1 and P1-12.

**P0-3 · Mega-tool routers missing `admin_only`.** `chrome_cookies`, `chrome_webmcp`, `cdp_session`, `cdp_emulate` have zero `admin_only` in `canonical-mergers.ts`, though their categories and wrapped handlers are admin-only. `chrome_webmcp` also declares no `required_optional_permissions` → no backstop at all. *Why:* routers are advertised to non-admins and (pre-P0-2) reach the dispatcher with no admin/perm gate. *Fix:* add `admin_only: true` to those four routers. **S.** Largely subsumed once P0-2 lands, but the flags should still be correct for advertisement.

**P0-4 · SW restart mid-stream drops tool results → agent hangs forever.** Dispatcher `runs` Map is in-memory (`dispatch.ts:66`); offscreen broadcasts `STREAM_OPENED` once and never re-emits (`offscreen/main.ts:61`). After a ~30s idle reap mid-run, the next `tool_delegated` finds an empty map: conversationId null → result never POSTed (hang), permissionMode silently → 'ask', assignedTabId null → tab drift. *Fix:* persist `RunMeta` per runId to `chrome.storage.session` (write at STREAM_START/OPENED, read-through in the chunk handler) **or** have offscreen attach `{conversationId,permissionMode,assignedTabId}` to every chunk envelope. **M.** Highest-leverage single fix.

**P0-5 · SW death mid-approval orphans the pending confirm.** The confirm wait is an in-memory Promise + setTimeout in a fire-and-forget `handleCall` (`dispatch.ts:703-743`); nothing keeps the SW alive during the up-to-5-min window. On reap: card persists, user clicks Allow, the response wakes a fresh SW with no listener → tool never runs, no result, run stuck; the 5-min fail-closed timeout is also gone. *Fix:* persist pending-confirm records to `chrome.storage.session`, re-attach the response→run path on boot (or drive the timeout via `chrome.alarms`). **M.** Same mechanism as P0-4.

**P0-6 · Agenda runs are structurally broken (subscribe-after-stream).** `runTask` does `await send(...)` *before* subscribing to STREAM_OPENED/CHUNK and before populating `inFlightByTaskId` (`runner.ts:104-173`), but that `send` only resolves after the entire SSE (incl. `done`) completes. Result: `markRunStarted`/`finishRun` never fire → **every run stuck "claimed" forever**; `inFlightByTaskId` set post-stream (backwards) → after the first run, re-runs are permanently blocked until reload; heartbeat `persistent_conversation_id` never captured → **forks a new conversation every pulse** (heartbeat memory is fiction). *Fix:* pre-generate the runId, subscribe + set in-flight BEFORE `send`, filter by runId. **M.** Unblocks the entire scheduler stack.

**P0-7 · Agenda same-device double-run.** `next_due_at` is advanced only after the run ends (`scanner.ts:108-128`); the +60s alarm refires while it's stale, and the `isTaskRunning` guard is broken by P0-6. *Fix:* advance `next_due_at` (CAS-guarded `.lte(observed)`) BEFORE dispatch; add a module-level scan mutex (also fixes boot-scan vs alarm-scan overlap). **M.** dep: P0-6.

**P0-8 · No CI; production build never typechecks.** `.github/` absent — nothing enforced on PRs. `build` = `wxt build` (esbuild per-file, no whole-program types); `compile` (`tsc --noEmit`) is separate and never invoked; `prebuild` drift is `|| true`. *Why:* a type error or drifted schema ships to the Web Store. *Fix:* add `.github/workflows/ci.yml` running `tsc --noEmit` + `biome check --error-on-warnings` + `vitest run` as required checks; add `tsc --noEmit` to the real build chain. **M.**

**P0-9 · Release scripts broken on Linux.** `release.sh:172,189,226` + `ship.sh:41` use macOS-only `sed -i ''`; GNU sed misparses it → the manifest-key comment-out dance silently fails, and the EXIT trap can leave `wxt.config.ts` with the key commented out (breaks dev OAuth). *Fix:* portable `sed -i.bak -E ... && rm -f *.bak` or `perl -i -pe`. **S.**

**P0-10 · Audit receipt lost-update race.** `appendReceipt` is a non-atomic read-modify-write on a `chrome.storage.local` array (`log.ts:35-49`), fired via `void` from the dispatcher; parallel/pilot fan-out (≤8 concurrent) races the same array → receipts silently dropped. *Why:* the chain-of-custody feature loses records exactly where integrity matters most. *Fix:* serialize through an in-module promise queue (`tail = tail.then(doAppend)`). **S.**
