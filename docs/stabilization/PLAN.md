## Build and reload contract — included in every procedure

Every test and retest begins with a resource permit and a build receipt: source SHA plus dirty-source hash when applicable, lockfile hash, output hash, WXT mode, extension runtime ID, Chrome version, profile label, auth/role/org state, permissions, backend identity, fixture IDs, and timestamp. No secrets in receipts.

Receipts also declare login method, principal provenance, real data origin, build/env flags, response interception, mocks and seeded browser state. A real controlled test page is allowed and identified. Mock-backed/component/unit results are supporting evidence only; closure requires actual UI sign-in and real backend reads/writes without mocked service responses or injected sessions standing in for the authentication flow. Verify the effective running configuration rather than trusting a worker's label.

Wait for build completion; reload the extension when background, manifest, permissions, config or environment changes require it; reopen extension pages and the side panel; reload controlled target tabs to replace injected content scripts. Treat offscreen and service-worker contexts separately. Verify their running build before acting. HMR alone is not acceptance proof. Never use manifest version alone to identify development builds.

MV3 service workers may terminate when idle. Exercise restart/persistence with DevTools closed, since inspection can keep the worker alive. Separate normal idle restart from crash evidence. Confirm offscreen recreation and message routing for the surfaces being tested. Include warm run, cold/reloaded run, page navigation and relevant permission-denied/offline recovery cases. Record a lifecycle fault only after the correct rebuild/reload sequence.

Independent closure retests also use a fresh unpacked non-HMR build. Record build mode so dev-server behavior cannot hide production lifecycle defects. Release builds and dev builds must not race over output directories.

Sources: https://developer.chrome.com/docs/extensions/get-started/tutorial/debug ; https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle ; https://wxt.dev/guide/essentials/config/browser-startup .

### Runner diagnostic acceptance
Before the first launch of a new acceptance runner, its source reviewer must verify that every potentially failing boundary records a fixed stage/target and the last safe observable booleans or counts. An opaque catch that reports only “unverified” is insufficient. Never serialize raw auth URLs, errors, credentials, tokens, storage values, or unrestricted page text. After repeated native hit refusal, obtain a safe targeted screenshot/hit-element observation or hand the real click to the native operator before another speculative repair. This rule follows repeated fixture failures that consumed runs without identifying their failing boundary.

## One inventory, linked durable evidence

Home: `docs/stabilization/`. `inventory.json` is the only authoritative scope/coverage register. Supporting records contain evidence, not competing feature status. Coordinator alone merges canonical status; workers write uniquely owned evidence/report files. All authored tracking files are committed and pushed frequently.

Each feature has stable ID `EXT-F-0001` (never renumbered/reused), parent feature if any, name, owning surface, entry points, individually identified controls/actions, source anchors, applicability rules with evidence, dependency class, wave, owner, case IDs, and explicit mode cells. IDs are allocated centrally in disjoint ranges.

Required mode axis: guest, signed-in admin, and signed-in ordinary member wherever behavior differs. Device org unset/set/switching, role, permission, session-expired and relevant service-availability states are dimensions of cases, not substitutes for auth modes. Each feature × mode cell tracks applicability (`applicable|not-applicable` plus reason), test status (`unverified|running|pass|fail|blocked|stale|not-applicable`), linked run IDs, linked defect IDs, retest status and last verified build. Terminal verdicts are pass, fail or evidenced not-applicable; blocked/unverified/stale are visibly unfinished. A denied or hidden feature still gets a negative access case where needed; not-applicable never excuses an access-control check.

Build channel is an additional case dimension: development-only controls and Store-omitted entry points must be identified explicitly. Local-development success is not a claim that a control exists in the Store package.

For org-scoped data, pair an authorized positive control with a real second-organization/non-member denial through the actual product/data door. Switching two organizations as the same all-access admin is not a non-member check. Missing suitable test principals or memberships leaves that boundary unverified and enters the consolidated access checkpoint; never weaken permissions to make a test run.

`defects/EXT-D-0001.json`: stable ID, feature ID, control/case ID, surface, auth mode, role/org/permissions, preconditions, precise numbered reproduction, expected, actual, sanitized evidence references, build receipt, reproducibility count, severity, priority, state, owner, root cause, sibling census, fix commit(s), original-repro retest run, surrounding-case runs, reviewer identity and transition history with timestamps/reasons.

Mandatory defect path: `open → triaged → in-fix → fixed → retest-pass → closed`; failure goes `fixed → retest-fail → in-fix`. Regression after closure appends a reopen event and returns to open/triaged; history is never overwritten. Duplicate/invalid reports keep an audit disposition and canonical link, never masquerade as a fixed defect. A report missing self-contained reproduction is returned for completion and stays open/untriaged. Evidence-backed intermittent faults remain open investigations; record attempts/frequency instead of throwing them away.

Severity measures user impact: S0 security/data loss or global outage; S1 a core action impossible; S2 material malfunction with workaround; S3 limited visual/usability defect. Priority independently sets order: P0 unblocks safe testing/global health; P1 current wave; P2 later contained/dependent wave; P3 deferred Chat/Pilot. Urgent Chat/Pilot regressions are logged and repaired promptly while daily guest Chat runs continue; deeper breadth remains deferred.

`runs/<run-id>.json` stores case outcomes, timestamps, receipts, resource admission, evidence paths and contamination/invalidation reasons. `reports/<task-id>.json` stores compact worker returns. `COORDINATOR.md` stores the restart procedure, current next actions, active agent IDs/ownership, unresolved blockers, and pointers. It does not duplicate coverage counts. `events.jsonl` stores meaningful transitions, integration changes and coordinator rulings. Raw credentials, browser profiles, cookies and unredacted logs/screenshots stay out of Git.

Coverage is generated exclusively by walking inventory cells and their linked cases/defects/runs: report counts and percentages for pass/fail/unverified/blocked/stale/not-applicable separately, per surface and auth mode. Denominator is every applicable cell, not just executed tests. Passing a feature requires every required control/case to pass. A report validator checks unique IDs, foreign keys, state transitions, required evidence and orphan work. New controls discovered later extend the inventory and remain unverified until tested; no work disappears outside it. Campaign progress reports count behaviors tested, defects reproduced, independently verified fixes, regressions, and releases, with source/native/Store evidence distinguished.

## 1. Dependency-ordered stabilization

Wave A: extension-local navigation and controls, local settings/state, inspection and browser-local utilities. Choose actual surface names/order from the census, not assumptions.

Wave B: remaining non-Chat/non-Pilot surfaces with direct persistence, organization/auth behavior, saved data and external integrations. Stabilize shared prerequisites before dependent controls. Treat each surface as a bounded unit and finish all its mode/control cells before moving on, except when a genuine external dependency allows independent work elsewhere.

Wave C: non-Chat/non-Pilot paths requiring desktop/web/backend coordination. Their local UI and refusal behavior can be covered earlier; systematic cross-system end-to-end work follows the contained baseline. Logging a dependency does not remove it from the non-chat completion gate.

Wave D: deeper Chat and Pilot work follows non-Chat/non-Pilot coverage. Daily guest Chat checks and urgent Chat/Pilot regressions run during earlier waves; log and route urgent findings promptly. If an external dependency prevents non-Chat completion, its gate stays visibly unmet. All deferred work remains inventoried.

Every surface gets exhaustive control/mode breadth, relevant adversarial boundaries, independent fix re-verification, and a final clean-build/release sweep. Optional owner feedback is welcomed but never required to keep the engineering loop moving.

## 2. Flat team and objective escalation

Maximum concurrent agents: owner plus three workers (actual platform limit). No worker creates managers, reviewer children or new chats. Owner dispatches a fresh independent reviewer. Browser/compute caps below are stricter than agent count.

| Lane | Model/effort | Work | Escalation threshold |
|---|---|---|---|
| Structured execution | GPT 6 Luna / medium | Narrow inventory slices, test batches, precise reproduction, independent straightforward retests | Two unusable/failed attempts, or 15 minutes without usable evidence: decompose once or route to Sol |
| Implementation | GPT 6 Sol / medium by default, low only for mechanical edits | Root-cause debugging, code, meaningful regression guard and self-verification | Two unsuccessful repair/retest rounds, second recurrence of the same regression, or 30 minutes without a verified increment: fresh Sol decomposition or Astra escalation |
| Exceptional escalation | GPT 6 Astra / low or medium | Hard cross-system issue or a recorded failed lower-tier attempt | One bounded 30-minute diagnostic assignment; return evidence and a concrete next move, never recursively expand the team |

Any non-building/non-running return is rejected immediately and consumes one failed attempt; it cannot advance to review. An infrastructure failure invalidates the affected run and routes environment repair, not a guessed product defect. Budgets are configurable in the campaign policy; start with time limits because live token accounting may be unavailable. When available, capture actual token usage; do not claim a spend limit is enforced without a meter. Owner checks elapsed time and last artifact before additional dispatches; third failed review round is a circuit breaker requiring a changed hypothesis or scope split.

Each task names one owned slice, acceptance criteria, applicable modes, shared-resource permit requirements, report path and allowed files. Implementation return schema: `task_id, lane, model, status, feature_ids, defect_ids, summary, changed_files, commit_shas, verification[{case_id, run_id, verdict, evidence}], limitations, open_questions, next_action`. No raw transcripts. Full evidence lives on disk; chat return is at most 15 lines.

Builder self-verification is required before return. A fresh peer verifies the original reproduction AND surrounding cases in the UI. Review has separate behavior and code-quality verdicts; both must pass. Luna handles straightforward checks; Sol handles complex code/contract review. The owner receives this compact reviewed package and integrates it. The owner does not accept a builder's own assertion as closure.

Every user-visible fix updates `docs/feature-tests.md`; every shipped capability/state change updates the canonical extension state in common-docs. Reuse and link existing review-queue items; file independently verified UI work under the campaign lane without making owner feedback a prerequisite for continued engineering.

## 3. Resource admission and watchdog

Host-local policy: one heavy job or active browser test profile per host, with two hosted browser lanes only when they use isolated hosts, profiles, fixtures, and permits. A third worker may fix a defect while the owner coordinates; the owner plus three workers is the ceiling. Serialize any shared account, organization, secret staging, mutation fixture, backend state, or Store action that could contaminate another lane. Unrelated CI on another host does not itself stall admitted work here; load on the same host still counts. Workers launch only through admitted paths using the atomic host-local permit at `/var/tmp/matrx-stabilization-resource-<uid>`. Legacy leases and owned processes remain blocking on their host; machine locks/leases are outside Git, policy and receipts versioned. This approved operating policy still needs independent guard implementation review before two lanes are launched; never infer that the current guard already supports it.

The legacy bridge covers the default macOS TMPDIR, the current caller's TMPDIR, registered prior external TMPDIRs, live older guard processes, and discoverable inherited-token descendants. It is a cutover safeguard for this cooperative campaign, not indefinite compatibility with a separately started old script copy after the process census. Register any additional known prior external TMPDIR before admitting work through the new guard; an unknown dead legacy owner with no discoverable descendant cannot be inferred from an arbitrary volume.

For manual Chrome runs, `--profile-dir` must point to the actual browser user-data directory (on this host, `/Users/armanisadeghi/Library/Application Support/Google/Chrome`), never the repository as a substitute. For isolated runners, pass their actual temporary-profile volume. Use the guard's `statfs` available blocks; `df` may report a different APFS availability figure and cannot override a refusal.

Before launch, sample memory pressure, available-memory estimate, CPU load, swap growth and disk space on the repo/profile volumes. Refuse admission if memory pressure is not normal, available memory is below max(4 GiB, 20% physical RAM), mean sampled CPU busy over the full 60-second window is at least 75%, or mean busy is at least 60% and ANY sample in that window has one-minute load at least 75% of logical CPUs, free disk is below 20 GiB, swap grows over 256 MiB in 60 seconds, another heavy permit is active, or a required measurement fails. These are adjustable documented operational defaults, not product limits. On macOS use appropriate pressure/VM counters, not raw free pages alone.

Watch every 15 seconds during a job. Two consecutive unsafe samples block all new launches and ask the active owned runner to stop at a safe boundary; preserve diagnostics and mark affected verdicts invalid-resource, never product-fail. Resume only after three healthy samples and a fresh preflight. Atomic acquisition plus PID/start-time/run ownership prevents races. Reclaim a stale run lease only after confirming its owning process is gone and completing ownership-token cleanup across all process sessions. Failed cleanup or process measurement retains the lease; rerunning the guarded command retries stale cleanup automatically. Never kill unrelated processes or delete another contributor's state. An initial refusal is not permission to quietly lower thresholds.

Each `check`, `run`, and `browser` invocation writes guard-owned JSONL events to `docs/stabilization/resource-journals/<run-id>.pending.jsonl` before policy/command admission. Use a unique `--run-id` for every invocation; an existing pending or completed file refuses reuse. A check without an ID generates one and prints its path. The journal is mode 0600, syncs each guard event, and contains no child stdout or arbitrary error detail. After writing `RESOURCE_FINAL_DECISION` and closing successfully, the guard atomically publishes `<run-id>.jsonl`. Only that completed path can establish a resource verdict; a pending file remains unverified even if its last event says valid. Attach the completed journal to the run report and commit it with the report when the evidence is safe to retain. The final event records `resourceInvalid`, wrapper `exitCode`, and `decision` after cleanup. Missing final decision, missing watch evidence, a pending journal, or a journal write/close error means the resource verdict is unverified; never infer success from a child result. A write error while a permit is held retains the lease and visibly requires browser work to stop. Recovery follows the existing stale browser/owned-work procedure only after work has stopped.

Launch contract: `scripts/stabilization-resource.mjs run` admits only the concrete commands in `resource-policy.json`, plus positional test-file filters on its single-worker Vitest command. Install uses `--ignore-scripts`; preparation is a separately admitted WXT command. These trusted tools and their descendants must preserve `MATRX_RESOURCE_OWNER`; environment scrubbing, broker/daemon handoffs and arbitrary shell commands are forbidden. Process groups alone do not contain `setsid`: an inherited-token census covers discoverable detached tool sessions, and no launched run releases its permit until that census and group cleanup succeed. Daemonizing commands are forbidden. macOS hides some protected system-binary environments; those children must remain in the foreground process group. Arbitrary detached protected binaries or hostile descendants are explicitly outside the admitted trusted-command contract. This is cooperative trusted-tool ownership, not an OS sandbox. A WXT dev server holds the single permit until stopped; use a finished unpacked development build and stop the server before obtaining the manual-browser permit. Browser work stops before the holder receives Ctrl-C. If its holder died, an agent that has stopped manual UI work can retire its stale lease with `recover-browser --confirm-no-owned-work yes`; a live holder cannot be retired. Never bypass a retained lease by deleting its files.
