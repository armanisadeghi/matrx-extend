# D47 saved replay preparation visibility and cancellation candidate

Status: source candidate only. The installed observation is invalid because the native resource guard failed. This candidate addresses an independently proven source gap; it does not claim to fix that observation.

Apply the adjacent `candidate.patch.pending` to the product only after peer review and ownership transfer. It changes the local saved Network operation, leaving agent tool calls and organization approval holds alone.

The client first says `Connecting to saved replay…`. Once the service worker receives the Port request it says `Checking saved recipe and page…`. Immediately before the privileged card is requested it says `Waiting for your approval…`. The Network row offers Cancel throughout. Cancel aborts and disconnects the Port, restores the Run control, and displays `Saved replay was cancelled.`. The dispatcher rechecks the abort signal after any late preparation resolves, so cancelling a pending database or scripting operation cannot start capture. Navigation and unmount also abort the owned Port; stale outcomes stay hidden by the existing page-key and sequence guard.

No fixed preparation deadline is proposed. A pending organization choice or slow remote read is not an authorization to fail automatically. The visible stage plus Cancel makes the operation recoverable without claiming the dependency settled. The already existing approval expiry and capture-window/setup limits remain in force after their respective stages begin. A later operational deadline would have to use a feature-level admin knob, with real latency data and a separate review.

The UI regression keeps the actual PatternsTab and Port transport, with a parked runner dependency. On baseline source, the row has no Cancel control and the Port emits no connecting state. The separate dispatcher regression keeps the actual `runLocalSavedPattern`, preparation, and confirmation logic, parking only `fetchPatternsForDomain`. It asserts that preparation is visible before the read resolves and that cancellation prevents a late approval or debugger action. Both are red-capable candidates, not executed evidence. A second dispatcher case should park `chrome.scripting.executeScript` as a sibling boundary before final integration. A healthy installed run must then prove the exact stage sequence and approved capture with real rows.
