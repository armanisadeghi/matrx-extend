# Guest Chat backend organization timeline

## Finding

The backend failure is caused by an explicit guest organization policy introduced on **2026-09-26 12:48:22 PDT** in `aidream` commit `5b1deadf13231919b35b8020001ad907dccfe056` (`fix(orgs): no personal organization — guest reads its sole membership...`). Before that change, a fingerprint guest's funnel called the idempotent `public.ensure_personal_organization(user_id)` RPC when its request context had no organization. The commit deleted that on-demand personal-organization lookup and changed the guest branch to read active `iam.memberships` instead; it raises `GuestOrganizationRequiredError` unless there is exactly one membership. A guest with zero active memberships therefore receives the observed exception. This matches the live reproduction: the extension's guest request reached the backend (HTTP 200 at the transport boundary), then failed inside the streamed response because the fingerprint guest had zero active organization memberships.

This is a functional mismatch for guest Chat: its no-login request enters with no organization and the general chat funnel expects a pre-existing sole membership. The new behavior follows the commit's stated access-ladder rationale; it does not create an organization or membership for a fingerprint guest. The commit itself describes signup as provisioning one organization per account, while fingerprint guests are specifically not signed-up accounts. The runtime observation establishes the zero-membership state for this reproduction; this source trace does not establish why that particular guest identity had zero memberships.

## Relevant timeline

- **2026-09-25 13:27:00 PDT — `fbd1abb527`**, `fix(conversation): carry guest scope through every start`. Guest organization was installed at the AI funnel; guest code used its personal-organization resolver. This is the immediately relevant earlier architecture, before the membership-only change.
- **2026-09-26 12:48:22 PDT — `5b1deadf13`**, the behavior change. `effective_org.py` replaced `_lookup_personal_organization` / `ensure_personal_organization` with `_guest_membership_organization`, which loads membership IDs and raises on zero or multiple results. `funnel_organization_id` calls it when a fingerprint context has no organization. The same commit changed the funnel test to expect refusal for `[]` memberships. Exact source: `aidream/services/organizations/effective_org.py:71-92,257-280`; test: `aidream/services/organizations/tests/test_guest_funnel_carries_its_organization.py`.
- **2026-09-27 05:24:45 PDT — `9c404a2ecd`**, `fix(guest): a signed-out run of a PUBLIC app acts in the app's own organization`. This added a narrow exception for runs of one published, public app: install the app owner's organization before the regular funnel. Its test explicitly records that before this change public-app guest runs failed with `organization_required: guest … has 0 active organization memberships`. The exception does not cover ordinary guest Chat (`chat.default_new_chat` is explicitly tested as not an app and remains refused). Exact source: `aidream/services/organizations/effective_org.py:379-424`; `aidream/services/organizations/tests/test_guest_public_app_run_acts_in_the_apps_organization.py:1-12,150-170`.
- **2026-09-29 01:52:57 PDT — `47bf15a663`**, `test: guard guest funnel block start boundary`. This strengthens ordering coverage so block-agent start validates and installs funnel organization before conversation writes. It does not change the membership requirement.

This trace identifies the introducing commit and policy mismatch, not the actual human actor. ## Later live database recovery and provenance

The incident follow-up reports that the live definition of `public._provision_new_user_organization` now calls `iam.provision_signup_organization(new.id)` for anonymous users, while the earlier trigger behavior did not. That would provide the membership the funnel requires, and it is a plausible explanation for recovery. It is a live SQL definition, not a migration or local `aidream` commit; local source history therefore does not date or identify this change.
