# Guest Chat backend organization timeline

## Finding

**Current truth:** guest Chat's backend request is recovered. The reported live SQL definition of `public._provision_new_user_organization` now calls `iam.provision_signup_organization(new.id)` for anonymous users. Historical runtime evidence proved the guest Chat request reached the backend (HTTP 200 at the transport boundary) and then failed inside its streamed response with `GuestOrganizationRequiredError`: that fingerprint guest had zero active organization memberships.

The membership requirement was introduced in `aidream` commit **`5b1deadf13231919b35b8020001ad907dccfe056`**, dated **2026-09-26 12:48:22 PDT** (`fix(orgs): no personal organization — guest reads its sole membership...`). Before that change, a fingerprint guest's funnel called the idempotent `public.ensure_personal_organization(user_id)` RPC when its request context had no organization. The commit removed that on-demand resolver and changed the guest branch to read active `iam.memberships`; it raises unless exactly one membership exists. This explains why a guest identity lacking a membership was refused. It does not by itself prove why that membership was absent. The later live SQL provisioning change is consistent with the signup side now meeting the funnel's contract, but its actor and time remain unknown.

Fingerprint guests are anonymous Supabase auth users, not non-users. The canonical signup contract provisions an organization for each new auth user, including anonymous users; the funnel policy requires the guest to have exactly one active membership. The defect evidenced here is that the required membership was absent for this runtime guest. The membership requirement is policy; the mismatch was between that requirement and the live anonymous-user provisioning behavior.

## Relevant timeline

- **2026-09-25 13:27:00 PDT — `fbd1abb527`**, `fix(conversation): carry guest scope through every start`. Guest organization was installed at the AI funnel; guest code used its personal-organization resolver. This is the immediately relevant earlier architecture, before the membership-only change.
- **2026-09-26 12:48:22 PDT — `5b1deadf13`**, the behavior change. `effective_org.py` replaced `_lookup_personal_organization` / `ensure_personal_organization` with `_guest_membership_organization`, which loads membership IDs and raises on zero or multiple results. `funnel_organization_id` calls it when a fingerprint context has no organization. The same commit changed the funnel test to expect refusal for `[]` memberships. Exact source: `aidream/services/organizations/effective_org.py:71-92,257-280`; test: `aidream/services/organizations/tests/test_guest_funnel_carries_its_organization.py`.
- **2026-09-27 05:24:45 PDT — `9c404a2ecd`**, `fix(guest): a signed-out run of a PUBLIC app acts in the app's own organization`. This added a narrow exception for runs of one published, public app: install the app owner's organization before the regular funnel. Its test explicitly records that before this change public-app guest runs failed with `organization_required: guest … has 0 active organization memberships`. The exception does not cover ordinary guest Chat (`chat.default_new_chat` is explicitly tested as not an app and remains refused). Exact source: `aidream/services/organizations/effective_org.py:379-424`; `aidream/services/organizations/tests/test_guest_public_app_run_acts_in_the_apps_organization.py:1-12,150-170`.
- **2026-09-29 01:52:57 PDT — `47bf15a663`**, `test: guard guest funnel block start boundary`. This strengthens ordering coverage so block-agent start validates and installs funnel organization before conversation writes. It does not change the membership requirement.

## Attribution and limits

Git author/committer metadata is a shared identity and co-author line; it does not prove which person or agent wrote, reviewed, or released the patch. This trace identifies the introducing commit and policy mismatch, not the actual human actor. No backend files or database rows were changed or queried, and no tests or browser runs were performed for this report.

That provisioning is consistent with the funnel contract and the reported recovery; the local evidence does not establish the exact causal sequence. It is a live SQL definition, not a migration or local `aidream` commit; local source history therefore does not date or identify this change.
